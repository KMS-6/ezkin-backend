# PR 크기·코드 리뷰 컨벤션

## 1. 목적

PR을 작고 명확하게 유지하여 코드 리뷰가 가능하도록 한다. 기능 구현, 리팩터링, 문서 변경이 한 PR에 뒤섞이지 않도록 관리한다.

## 2. 기본 규칙

- PR 하나는 하나의 목적만 가진다.
- 기능 구현과 대규모 리팩터링은 가능하면 분리한다.
- 관련 Issue를 반드시 연결한다.
- PR 설명에 변경 이유를 작성한다.
- AI를 사용했다면 사용 범위와 사람이 검토한 내용을 작성한다.
- 리뷰 승인 전에는 `develop` 또는 `main`에 병합하지 않는다.

## 3. PR 크기

- 권장: 문서를 제외하고 300~500줄 이내
- 1,000줄 이상: 가능하면 분리
- 분리 기준: 하나의 기능 또는 하나의 Issue 해결

이 기준은 가드라인이며 변경 범위와 리뷰 부담이 하나의 맥락으로 유지될 때 예외로 적용한다.

## 4. PR 제목

```text
[타입] 작업 내용
```

| 타입 | 의미 |
|---|---|
| `Feature` | 새로운 기능 추가 |
| `Fix` | 버그 수정 |
| `Refactor` | 기능 변경 없는 코드 개선 |
| `Docs` | 문서 수정 |
| `Test` | 테스트 코드 추가 및 수정 |
| `Chore` | 설정, 의존성 등 기타 작업 |

예:

```text
[Feature] 학생 Agent 기본 프로필 구조 추가
[Fix] 관계 업데이트 중복 적용 문제 수정
[Docs] AI 사용 컨벤션 문서 추가
```

## 5. PR 작성 항목

```markdown
## 작업 개요

이번 PR에서 변경한 내용을 간단히 설명한다.

## 관련 Issue

Closes #이슈번호

## 변경 내용

- 변경 사항 1
- 변경 사항 2

## 결정 사항 및 이유

이 구현이나 구조를 선택한 이유를 작성한다.

## 테스트 / 확인 내용

- [ ] 로컬 실행 확인
- [ ] 주요 기능 동작 확인
- [ ] 에러 케이스 확인
- [ ] 관련 문서 업데이트 확인

## AI 사용 여부

- 사용 여부: 사용함 / 사용하지 않음
- 사용한 작업:
- 사람이 검토한 내용:

## 리뷰어가 봐야 할 부분

특히 확인이 필요한 코드나 설계 포인트를 작성한다.
```

## 6. 코드 리뷰 코멘트 태그

| 태그 | 의미 |
|---|---|
| `[Must]` | 반드시 수정해야 하는 부분 |
| `[Question]` | 질문 또는 확인이 필요한 부분 |
| `[Suggest]` | 개선 제안 |
| `[Nit]` | 사소한 수정 |
| `[Good]` | 좋은 구현이나 유지하면 좋은 부분 |

예:

```text
[Must] 이 조건은 중복 적용될 수 있어서 분리해야 합니다.
[Question] 상태를 여기서 직접 변경하는 이유가 있을까요?
[Suggest] 함수명은 현재 의도를 더 명확하게 드러내면 어떨까요?
[Nit] 변수명 오타자만 수정하면 됩니다.
[Good] 이벤트 처리 로직을 별도 함수로 분리한 점이 좋습니다.
```
